# 竞赛定位与答辩材料

## 适用方向

- 中国国际大学生创新大赛 / “互联网+” 产业命题
- “挑战杯” 课外学术科技作品竞赛（信息技术组）
- 中国大学生计算机设计大赛（软件应用与开发 / 大数据实践）
- 开源创新、云原生、基础软件相关赛道

与常见的“AI 应用 + CRUD”项目不同，NimbusKV 主打 **基础软件与分布式系统**，答辩重点是算法正确性、工程可靠性和可复现实验。

## 一句话创新点

> 用零第三方依赖的 Python 实现一个教学可读、测试可复现、故障可注入的 Raft 分布式 KV 系统，把分布式一致性从“调用现成库”变成“看得见的工程”。

## 技术指标

| 指标 | 结果 / 验证方式 |
| --- | --- |
| 多数派提交 | 3 节点中 1 节点故障仍可读写 |
| 自动故障转移 | `benchmarks/fault_injection.py` 循环杀 leader |
| 数据不丢失 | WAL `fsync` + 原子快照，测试覆盖重启恢复 |
| 线性一致读 | heartbeat quorum 后再返回状态 |
| 日志压缩 | 超过阈值触发 snapshot，落后节点走 `InstallSnapshot` |
| 客户端无感 | leader 自动发现与重定向 |
| 零依赖 | 仅 Python 标准库，CI 可一键复现 |

## 演示脚本

1. 启动三节点集群。
2. `put` 写入一条数据，`get` 读回。
3. 打开 HTTP dashboard，展示 leader/follower/term。
4. 手动杀掉 leader 进程。
5. 展示 status 中新的 leader，再次 `get` 成功。
6. 运行 `python benchmarks/fault_injection.py --rounds 10`，展示平均恢复时间。

## 评委可能追问

**Q：为什么不用 etcd / hashicorp/raft？**
A：本项目定位是底层实现而不是工程集成。从零实现可以展示对安全性规则的完整理解；工程中使用当然应选经过生产验证的成熟库。

**Q：Python 性能不够怎么办？**
A：本项目的目标是正确性和可读性。协议层与状态机已解耦，性能瓶颈可通过二进制协议、批量提交、Rust/Go 重写热路径优化。

**Q：如何证明一致性？**
A：通过三个层面：单元测试覆盖日志冲突与持久化；三进程集成测试覆盖真实网络和杀 leader；故障注入脚本提供重复实验数据。

**Q：网络分区时会脑裂吗？**
A：不会。Raft 的 term、投票唯一性和多数派提交规则保证同一 term 最多一个 leader，旧 leader 无法获得多数派确认，线性一致读也会因 quorum 失败而拒绝返回过期数据。
